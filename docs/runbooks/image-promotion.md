# Image builds and deployment PRs

Each application source repository owns its container image on protected `main`. The workflow file is `.github/workflows/image.yml` in `xenomit-orchestrator`, `xenomit-web-panel`, and `xenomit-botd`. Jobs run on the `xenomit-build` runner group, publish to `ghcr.io/xenomit-do/xenomit-<name>` with SBOM/provenance and keyless Cosign signatures, then use a narrowly scoped GitHub App token (`Actions: write` only) to dispatch the `promote-image.yml` workflow in `xenomit-deployments` with digest metadata. No Actions artifact uploads or hosted compute are used.

`xenomit-deployments` validates the image key, source repository, digest, and commit, then opens a digest-only PR against `apps/control-plane/kustomization.yaml`, `apps/panel/kustomization.yaml`, or `fleet/botd-image.json`. Its workflow mints a separate short-lived App token (`Contents: write` + `Pull requests: write`) so the PR triggers normal required checks. Merge after `source-check` passes, then set `enable_applications=true` and apply the services stack. The fleet stays empty until desired Bot CRs and disposable runtime credentials are supplied; `fleet/botd-image.json` records the botd digest for reviewed desired-fleet changes and is not a Kubernetes object.

## GitHub App and org secrets

Install a dedicated GitHub App (or reuse an existing automation app) on `xenomit-deployments` only, with **Actions: write**, **Contents: write**, and **Pull requests: write** on that repository. Do not grant platform administration or org-wide contents. Store `APP_ID` and `APP_PRIVATE_KEY` as organization Actions secrets, restricted to the three source repositories and `xenomit-deployments` (selected repositories, not all repos). Source `image.yml` workflows request only an `Actions: write` installation token to start the one promotion workflow. The deployments workflow requests only `Contents: write` and `Pull requests: write` when creating a digest PR.

Grant each source workflow `packages: write` and `id-token: write` so GHCR publish and Sigstore keyless signing succeed. For existing packages originally published by the platform workflow, grant each corresponding source repository package write access in GHCR package settings (or transfer/link the package to its owning source repository); `GITHUB_TOKEN` is repository-scoped. Make the three packages public for cluster pulls, or supply a read credential using IaC before enabling applications. Repository visibility does not automatically make container packages public.

## Sibling sources and IaC

The botd image build consumes immutable sibling commit pins in `xenomit-botd/ci/source-pins.json`; orchestrator similarly records its required sibling pins. Update these pins deliberately and validate the Rust lockfile against the exact materialized workspace. Missing Dockerfiles, source directories, or upstream images fail the build instead of deploying mutable tags. Do not publish the proprietary Pepper plugin or secrets: mount runtime assets through the documented local credential setup.

Runner groups and admission policy are enforced in OpenTofu. After changing `infra/10-external/automation.tf` or `infra/30-services/policies/verify-signed-images.yaml`, apply the external and services stacks so `xenomit-build` permits the three source image workflows, `xenomit-platform` permits the deployments promotion workflow, and Kyverno accepts signatures only from the three source `image.yml@refs/heads/main` identities (not the platform repo).

Active admission policies require organization GHCR digest pins and a signature from one of the trusted source workflows. Third-party Vault is exempt from application pod policies and remains isolated by its network policy. Legacy local-registry policies are retained only for migration reference.
